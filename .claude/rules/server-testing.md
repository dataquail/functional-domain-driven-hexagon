# Rule: server test seams

**Scope:** `packages/server/` (and `@org/jobs`) — read before writing or running tests.
**Backing ADR:** 0009 (testing pyramid).

- **Use-case unit tests** (`commands/`, `event-handlers/`) compose three test-only services: `UserRepositoryFake`, `RecordingEventBus`, and `PassThroughUnitOfWork` from **`@effect-server-utils/unit-of-work/testing`** (the real boundary over an in-memory driver — it installs the real `DeferralSink` too, so a subject that dispatches an event gets production's delivery). No DB, no docker.
- **Four test kinds, told apart by filename stem, each with its own allowlist** (the `server-*-test-file` fragments in `packages/server/architecture.yaml`). A _unit_ test (domain, the fakes, `*.util.test.ts`, `*.endpoint.test.ts`) names `effect`, `@effect/vitest`, node's assert and the server. A _use-case_ test (`commands/`, `event-handlers/`, `sagas/`, `acl/`, `*.event-adapter.test.ts`) adds `@effect-server-utils/cqrs` and `@effect-server-utils/unit-of-work`. An _integration_ test (`*.repository-live.integration.test.ts`, `queries/*.integration.test.ts`) adds `vitest` and `@org/database`. An _endpoint_ test (`*.endpoint.integration.test.ts`) adds `@org/contracts` and the bus it seeds through. Three nodes name one more thing at the node itself: the client tests their SDK, the `criteria-to-sql` test the SQL driver, the policy tests the contracts' errors. Unit tests import `@effect/vitest`, never plain `vitest`. A test that needs more than its kind grants is a test of the next kind — rename it, don't widen the fragment.
- **Two disjoint suites, selected by file suffix + the `TEST_INTEGRATION` env toggle** (in `vitest.shared.ts`). `pnpm test` runs the **unit** suite — every `*.test.ts` _except_ `*.integration.test.ts` — and needs no auxiliary services. `pnpm test:integration` (sets `TEST_INTEGRATION=true`, scoped to `@org/server`, `@org/jobs` and `@org/identity`, one after another) runs **only** `*.integration.test.ts`. The suites never overlap. `@org/identity`'s integration tests run Better Auth against an identity database its global setup creates beside `DATABASE_URL_TEST` (`<name>-identity`) and migrates.
- **Workerd smoke tests** (`packages/infra/smoke/*.smoke.test.ts`, `pnpm test:workers`, selected by `TEST_WORKERS`) boot the Workers stack with Alchemy's `Test.make({ dev: true })` and drive the server Worker's `fetch`, `queue` and `scheduled` over HTTP. They prove the bundle runs in workerd, not behaviour — that stays in the unit and integration suites. They need the docker Postgres and free dev ports (:3001, :3002), so they are a named gate beside `check:all`. `@cloudflare/vitest-pool-workers` is not an option: it peers on vitest 4.
- **Integration tests** (`*.repository-live.integration.test.ts`, `<endpoint>.endpoint.integration.test.ts`, `<query>.handler.integration.test.ts`) hit a real DB and are **dumb** — they do not self-skip. The integration global-setup hard-fails (asserts `DATABASE_URL_TEST` is set, then connects) so a missing or unreachable DB aborts the whole run rather than silently skipping. Provide `DATABASE_URL_TEST` (name must contain `test`) before running `pnpm test:integration`.
- **HTTP integration tests** use `useServerTestRuntime(["table1", "table2"])` from `test-utils/`, which wires `ManagedRuntime.make(TestServerLive)` + `beforeAll`/`afterAll` + per-test `truncate`. The API is served the way the Worker serves it, through a Web `Request` handler: `test-utils/test-http-server.ts` is an `HttpServer` that listens on nothing and an `HttpClient` whose fetch calls the served app, so no socket or Node server is involved. Tests then exercise the contract via `HttpApiClient.make(Api)` and seed prior state by calling _other endpoints_, not by reaching into module internals.
- **Query/repository integration tests** seed via the live repository (or other production-path code), not via raw SQL. Using the repository as the seeding seam keeps the test honest about what production paths look like.
- **Coverage is one merged number, and it gates CI.** The unit and integration suites each miss code the other covers, so neither is gated on its own: `pnpm test:coverage:unit` and `pnpm test:coverage:integration` write Vitest **blob** reports into `.vitest-reports/`, and `pnpm coverage:merge` folds them into one report and checks the thresholds. `pnpm coverage` runs all three locally (needs `DATABASE_URL_TEST`). Coverage config is root-only — a project config's `test.coverage` is ignored in workspace mode, and a per-package run drops every file outside that package's root, so `vitest.config.ts` at the repo root owns `include`/`exclude`/`thresholds` and every coverage run is a root workspace run. Thresholds turn on only for a `--merge-reports` run. They are a **ratchet**: raise a floor when coverage rises, and never lower one to make a red build green — the fix is a test. Files a Vitest suite can never reach (process entrypoints, resource declarations) are excluded rather than discounted; a view or endpoint that merely lacks a test is not.
- **Endpoint test naming.** A test file ending in `*.endpoint.integration.test.ts` exercises the real HTTP layer against a live database via `useServerTestRuntime(...)`. A file ending in `*.endpoint.test.ts` is a true unit test — no DB, no HTTP round-trip — typically a parity-rule token for endpoints whose meaningful coverage lives elsewhere (the OIDC `login` / `logout` flows, covered by Playwright + `SessionRepositoryLive` integration tests; `callback`'s reachable no-IdP guard has a real `callback.endpoint.integration.test.ts`). The `login`/`logout` endpoints are the two named exemptions on the `endpoint-test` parity rule (its `fileNot`); every other endpoint must have `*.endpoint.integration.test.ts`. Any `.endpoint.test.ts` file must carry a header comment naming where the meaningful coverage lives; if a test starts hitting real HTTP + DB, rename it to `.endpoint.integration.test.ts`.
