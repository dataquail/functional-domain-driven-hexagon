# Rule: server module layout

**Scope:** `packages/server/src/` — read before adding/moving files in a feature module.
**Backing ADRs:** 0002 (module layout), 0003 (aggregates/events), 0013 (HTTP endpoint files), 0020 (per-module DB schemas), 0022 (cross-module ports), 0023 (domain services / interface utils), 0024 (dot-delimited filenames), 0032 (module imports and exports).

Each feature module lives at `packages/server/src/modules/<feature>/` with sibling folders. There is no `application/` umbrella — commands, queries, and event-handlers are siblings, each with its own `imports` allowlist in `packages/server/architecture.yaml` (see ADR-0008, ADR-0027, ADR-0031).

- `domain/` — events, errors, ports (see `domain/ports/` below), and the DDD stereotypes below. Each stereotype carries an explicit filename suffix and a matching identifier-keyword suffix so its role is legible at a glance:
  - **Aggregate roots** — `*.root.ts`. The root data type is `XRoot` (a `Schema.Class`). Operations are **pure free functions** collected into an `export const XRootOps = { … } as const` bag — the data stays a dumb value (no methods/statics on it). Consumers `import { XRoot, XRootOps }` — there is no `import * as`. Only `*.root.ts` carries a test-parity obligation. Lifecycle default: carry state in flag/nullable columns and let each op guard its own invariants and return `Result<Outcome, DomainError>` (`effect/Result`; `Outcome` is the op's success payload: new state + emitted events. Consume inside a handler's `Effect.gen` via `yield* Effect.fromResult(...)`, since v4 `Effect.gen` does not adapt a yielded `Result`), so invariants are enforced in the domain once; model states as distinct variant classes unioned into `XRoot` only when states carry divergent data or a large transition matrix warrants it — see ADR-0003.
  - **Constituent aggregates** — `*.aggregate.ts` (a collection of entities/VOs that is only a _part_ of a root, not itself a consistency-boundary root). No parity obligation.
  - **Entities** — `*.entity.ts`, identifier `XEntity`.
  - **Value objects** — `*.value-object.ts`, identifier `XValueObject` (attribute-bag, no identity of its own).
  - **Branded IDs** — `*.id.ts`, identifier `XId`. An identifier is technically a value object, but it gets its own category: it already carries its keyword (`Id`) and denotes an entity's identity rather than being an attribute-bag.
  - **Errors / events** — `*.errors.ts`, `*.events.ts`.
  - **Filename convention (ADR-0024):** every stereotype is a dot-delimited suffix (`.command`, `.repository`, `.handler`, …); dashes appear only _within_ a concept name (`api-token.repository.ts`, `find-users.query.ts`). Compound stereotypes keep internal dashes as one segment (`.repository-live`, `.event-adapter`, `.value-object`).
  - **Domain services** — `*.domain-service.ts`, a pure free-function bag (like `RootOps`, no DI Tag) for stateless domain logic **no single aggregate owns** (ADR-0023). Test-obligated. Guard against anemia: only for logic with no aggregate home (e.g. `CredentialHash`, applied to raw lookup input across aggregates); logic that operates on one aggregate stays on its `RootOps`. Randomness never lives here — it's impure, so it stays in the command (the shell).
  - **Ports** — `domain/ports/`, tiered by counterpart (ADR-0022); no port sits directly in `ports/`. `ports/repositories/*.repository.ts` (own datastore), `ports/clients/*.client.ts` (true third-party systems), `ports/acl/*.acl.ts` (other bounded contexts). The tier decides the anti-corruption obligation and, for `acl/`, which infrastructure adapter may import a foreign barrel.
- `commands/` — write-side use cases. Each has a `<verb-noun>.command.ts` declaring the message with `Command.make` (payload/success/failure schemas, plus an exported `<Name>Payload` type) and a `<verb-noun>.handler.ts` handler taking that payload. The module's `<feature>.command-handlers.ts` collects the definitions into a `Command.group` and binds handlers with `Command.handlersOf`. **Identifiers carry the stereotype** (ADR-0024): the definition is exported as `<Name>Command` — the same string as its dispatch tag — and the handler as `<name>Handler`, whose `Effect.fn("<name>Handler")` span label matches. The payload type stays `<Name>Payload`.
- `queries/` — read-side projections. Same `.query.ts` schema + `.handler.ts` handler split, and the same identifier rule — `<Name>Query` (matching the tag; `.policy-query.ts` included) and `<name>Handler`. A query **must not** reach the write-side consistency boundary: it builds its own read model by reading SQL directly via `@org/database` (the shared `RowSchemas.*` are the reusable read-model kernel), never by loading an aggregate through a repository. From its own `domain/` it may import only two non-write-model things: branded IDs (`domain/<sub>/*.id.ts`) and cross-context ACL ports (`domain/ports/acl/`, since ADR-0020 bans cross-schema SQL); roots, ops, repositories, specifications, value-objects, errors, and events are off-limits (enforced by `queries-isolation`). Read-side errors/statuses live in the `.query.ts` (query-owned), not the domain. A query published so **other** modules' authorization checks can ask it a question is named `*.policy-query.ts` (ADR-0022) — same mechanism, but it is a cross-module contract with a stability obligation an internal `*.query.ts` does not have; consumers reach it only through their own `domain/ports/acl/` adapter. Use-case DB reads are tagged-template statements off the client (`const sql = yield* Database.Database`), decoded with `Database.rows`/`maybeRow`/`row`. Joining the ambient unit-of-work transaction is automatic — the client resolves the transaction connection before every statement and falls back to the pool when there is none — so a policy/ACL query resolved during a command's authorization is correct without an opt-in. This used to be a per-call choice (`db.makeQuery` vs `db.execute`) policed by a lint rule; both are gone.
- `event-handlers/` — write-side use cases (`*.handler.ts`) reacting to internal triggers (`event-handlers/triggers/<publisher>.triggers.ts`). Run in the publisher's fiber and inherit its transaction (ADR-0007). Same dependency shape as `commands/` — no cross-module barrel imports.
- `infrastructure/` — driven adapters, tiered by counterpart to mirror `domain/ports/` (ADR-0022); private to the module. `infrastructure/repositories/` (`*.repository-live.ts` + `*.repository-fake.ts` + `*.mapper.ts`), `infrastructure/clients/` (third-party adapters: `*.client-live.ts` + `*.client-fake.ts` behind a `*.client.ts` port, self-contained `*.client.ts` clients, `*.email.tsx` templates), `infrastructure/acl/` (anti-corruption adapters to other modules: `*.acl-live.ts` + `*.acl-fake.ts` behind a `*.acl.ts` port — the only place, besides `interface/events/`, permitted to import a foreign barrel).
- `sagas/` — `*.saga.ts` process managers over **post-commit** events, one per saga, each with a sibling `*.saga.test.ts`. A saga correlates several events over time and compensates when a later step fails; if one event decides the outcome it is an `interface/events/` adapter instead. Bus-only like an adapter (`sagas-isolation`): own events/ids, own `*.command.ts`, `@effect-server-utils/cqrs`, `platform/ids/`, foreign barrels for cross-module events — no repositories, no ops, no `@org/database`. A saga runs on its own fiber with no publisher transaction to inherit, so a repository call here would write outside every unit of work.
- `interface/` — inbound adapters, one subfolder per protocol:
  - `interface/http/` — one `<endpoint-name>.endpoint.ts` per HTTP endpoint (ADR-0013), plus an `index.ts` barrel that registers the endpoint groups. May also hold `*.util.ts` — pure, leaf, test-obligated protocol/wire helpers shared between endpoints (ADR-0023). `*.util.ts` is allowed **only** in `interface/http/` and `interface/cli/` — never in the application layer (commands/queries/event-handlers), where a shared helper is a smell (it's domain logic → an aggregate op, or trivial → inline). A leaf rule bars utils from importing ports, use cases, infrastructure, buses, or barrels.
  - `interface/events/` — one `<publisher>.event-adapter.ts` per upstream module whose domain events this module consumes (ADR-0007 ACL). The only place in the consumer module permitted to import another module's barrel.
- `policies/` — `*.policies.ts` registry, `*.resource-resolver(s).ts`, and `is-*.policy.ts` checks. The DSL itself is the standalone `@effect-server-utils/authz` package (`Check`, `CheckFor`, `ResourceCheck`, `CallerCheck`, `Resolver`, `PolicyContribution`); a module augments `PolicyMap` / `ResourceResolverMap` with `declare module "@effect-server-utils/authz/policy-registry"` / `"@effect-server-utils/authz/resource-resolver-registry"`. The four host types the library does not own — caller, check failure, resource-missing, and the **action vocabulary** (this app's CRUD set lives in `platform/auth/actions.ts`; the library ships none) — are declared once in `platform/auth/authz.ts`, which also builds `hasPermissions` — that file is the only server-side authz configuration, and it is listed in `tsconfig.test.json`'s `include` so its augmentation reaches the test program. There is no `policies/public/`: a module does not publish an ACL service for other modules' policies (ADR-0022). A check takes its data source as an argument and the module's contribution — an effectful Layer behind a Tag — closes over it, so every registered check is `R = never` and a policy test provides nothing. Foreign data comes from this module's own `domain/ports/acl/` port; own data from dispatching this module's own query. Policies read **read models only** — never a root, repository, or specification (enforced by `policies-isolation`).
- **Module root** — a closed set of aggregation/composition files only, each a dot-delimited stereotype named for the plane it serves (ADR-0024): `<feature>.platform.ts` (what the platform names), `<feature>.exports.ts` (what a peer names), `<feature>.imports.ts` (what this module takes from other modules), `<feature>.module.ts` (the module's Layers), `<feature>.command-handlers.ts` / `<feature>.query-handlers.ts` (bus-registration maps), `<feature>.event-span-attributes.ts`. There is no `index.ts`: a module root has no file whose name doesn't say what it is. Any other file must move into a subfolder — enforced by `architecture/structure` (see the file-taxonomy rule).
  - `<feature>.module.ts` exports one value, `<Feature>Module`, a plain record of up to three Layers. They stay separate fields rather than one merged layer because the composition root provides them at three different depths of the server pipeline: `layer` (the dispatch surfaces) below the buses that route them, `http` (the endpoint groups) into `HttpApiBuilder.layer`, and `httpDeps` (services an endpoint resolves per request) into the result of `HttpRouter.serve`. Only the last of those needs explaining: providing such a service onto its own group layer leaves it in that layer's requirements, because `HttpApiBuilder` carries a handler's requirement through to the assembled api and only `serve` unwraps it. A module with no HTTP surface simply has no `http` field.
  - **A module states its own imports by providing them** (ADR-0032). `<Feature>Module.layer` closes over every module it reaches: `Layer.provide(RoleModule.layer)` for each one, named directly from that module's `<feature>.module.ts`. `provide` is a private import — the provided module does not appear in this module's output — and `provideMerge` is a re-export. There is no ordering anywhere: the composition root is a `Layer.mergeAll` over the set, and Effect's layer memoization is what keeps a module provided at several sites a single instance.
  - **Each plane has one gateway in and one out, and they do not mix.** On the coupling plane, `<feature>.exports.ts` publishes and `<feature>.imports.ts` consumes: the messages a module dispatches, the domain events it reacts to, and any service a peer offers. It is the only file in the module that may name another module's vocabulary, so an ACL adapter and an event adapter read their own module's gateway rather than reaching a foreign surface. On the wiring plane, `<feature>.module.ts` both publishes Layers and names other modules' `<feature>.module.ts` to provide them — assembly talking to assembly. A Layer never appears on either coupling file: needing one is a fact about how the application is assembled, not something a bounded context asks of another. `architecture/imports` refuses every crossing, in both directions.
  - **Coupling and wiring are still different planes on the way out.** `<feature>.exports.ts` is the PEER surface — the vocabulary another bounded context is genuinely coupled to, reachable only from a consumer's `infrastructure/acl/**` or `interface/events/**`. `<feature>.module.ts` is the WIRING plane — the module's Layers, reachable only from another module's `<feature>.module.ts` and from its own `<feature>.platform.ts`. `<feature>.platform.ts` is the PLATFORM surface, reachable only from `@/server.ts`, `@/platform/**`, `@/test-utils/**` and tests; no module may name another module's.
  - **A Layer is not a peer export.** Needing one is a fact about how this application happens to be assembled, not about what one context asks of another — so it never appears on `<feature>.exports.ts`, which would put incidental DI coupling next to the real thing and make an ACL adapter drag a whole module's assembly in behind a message contract. Application code that reaches for a Layer is application code in the wrong plane; `architecture/imports` refuses it. Publish nothing on either plane without a consumer: 35 of 39 message definitions had none.
  - **What the peer surface declares is named `<module>Access<Queries|Commands|DomainEvents|Errors>`** — `roleAccessQueries`, `userAccessCommands`, `organizationAccessDomainEvents`, `userAccessErrors` — one shape across every module, enforced by `architecture/surface` on `<feature>.exports.ts`. A consumer's import line then says which bounded context it is reaching and whether it is asking, telling or listening, and a second subset for a second consumer is a rename rather than a new vocabulary. Domain events, and errors from a published failure channel that a peer has to name to translate, are each collected into their object rather than re-exported loose, so every grant is one name. **The peer surface may not re-export at all** — a bare re-export publishes whatever the origin happens to export under whatever name it happens to use, and slips past the naming rule; a peer that needs a type takes it off the published value (`InstanceType<typeof userAccessErrors.UserAlreadyExists>`, `typeof organizationAccessDomainEvents.OrganizationCreated.Type`). A type-only re-export is not exempted, because the extractor reads it identically to a value re-export. The prefix is held to a shape, not bound to the module's own name — a surface matcher does not interpolate the `{module}` capture.
  - **The peer surface carries both halves of what a peer may reach.** `Query.subsetOf(group, "OneTag")` / `Command.subsetOf` is the DI half — a group of exactly the messages a peer may dispatch, so a dispatcher built over it demands only those tags' registrations and adding a query to the module's own group cannot widen the grant. The re-exports beside it are the import half: the layer a peer provides, plus any domain vocabulary (an event, an error) a peer names rather than resolves.
  - **A module's policy contribution belongs in `<Feature>Layer`.** A policy dispatching its own module's queries resolves that module's dispatch surface, never the app-wide `QueryBus` — the bus aggregates every module's surface including this one, so naming it inside a module layer is a cycle.
  - **A real cross-module cycle is now an ES module cycle**, reported by `import/no-cycle` and by goodbones' `no-cycles`. There is no ordering to make one inexpressible, and no need for one.
  - **A service whose adapter differs between composition roots is the root's to provide, not the module's.** Billing's `BillingGateway` is the only one: production takes Stripe, the test runtime takes the fake, exactly as they already differ on the database, the auth middleware and the HTTP transport. It stays in the module layer's requirement channel; the module does not ship a second "fake" variant of itself, and `applicationModules` takes no parameters. `<feature>.platform.ts` publishes the live/fake pair — the one thing it may re-export from `infrastructure/`, and only for a `clients/` adapter, since a root picks a third-party seam but never a repository. Everything else a module needs, it provides.

Cross-module access leaves through the module's `<feature>.exports.ts`, which may not re-export from `infrastructure/` or `interface/` at all, and arrives through the consumer's `<feature>.imports.ts`. The published surface is domain types (events, IDs, errors) and the message subsets a peer may dispatch — never a Layer.
